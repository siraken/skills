# 外向きコミュニケーションの確認

他の人に届く文章(質問・依頼・報告・確認)を書くとき、投稿の前に必ずこの手順を通す。
相手の時間を使わせる行為なので、「聞かなくてよいことを聞く」「間違った前提で頼む」「届かない」を防ぐ。

## 1. 下書きの前に、状態を取り直す

会話の中で前に調べた内容は古いと考える。下書きを書く直前に取り直す。

- **課題・スレッドの最新**: 自分が最後に見たあとのコメント・ステータス・担当者の変更
- **ベースブランチの進み具合**: `git fetch` して、作業ブランチの分岐元と origin のベースブランチの差を見る。
  同じ画面・機能を他の人が並行して直していることがある(自分が足そうとしている変更が既に入っている、
  前提にしていた表示が既に変わっている)
- **関連する他の課題**: 同じ画面名・機能名・キーワードで課題管理ツールを検索する。
  別の課題で同じ論点が扱われ、すでに決着していることがある
- **相手側のリポジトリ・作業ブランチ**: 依頼する作業に相手がすでに着手していないか

取り直した結果、前提が変わっていたら、下書きを書く前にユーザーへその事実を報告する。

## 2. 聞く必要があるか(二度聞きの防止)

すでに答えがあることを聞くのは、相手の手間を増やし失礼になる。確認事項は、次を当たっても
答えが見つからないものだけにする。

1. 相手の直近の回答・コメント
2. 依頼本文とそのコメント(判断を委任する一文が無いか)
3. 関連する他の課題(上記の検索結果)。**特に、決定権を持つ人が別の課題で出した指示・確認**
4. 仕様書・設計書(該当箇所や補足・備考)
5. 実装(該当箇所のコード、既存コードの慣習)
6. 過去の PR/MR のレビューコメント

答えが見つかった項目は、質問から外して「〜のため、〜の更新が必要です」のような**連絡**に変える。
質問と連絡は文中で分けて書き、相手が「答えるべきもの」を一目で分かるようにする。

## 3. 事実の確認

送る前に、文中の事実を一つずつ根拠と突き合わせる。

- **数値**(件数・文字数・行数・幅など)は、推測や記憶で書かず、その場で数え直す・測り直す
- **固有名詞・識別子**(課題番号・MR 番号・コミット・ファイル名・パラメータ名・値の例)は実物と照合する
- **他人の発言の引用**は文脈を取り違えない。「確認した」「クローズした」を「合意した」「承認した」に
  強めない。根拠の強さに合った動詞を選ぶ(指示した/確認した/報告した/合意した)
- **「現状こうなっている」という記述**は、最新の状態(手順 1)で確かめたものだけにする
- 自分の以前の報告に誤りが見つかったら、黙って直さず、誤りだったことを明示して訂正する

## 4. 誰に・どこで・どう届くか

- **宛先とメンション**: 本文に名前を書くだけでは通知されないツールがある(API 経由の投稿など)。
  そのツールのメンション記法と通知先の指定方法を確かめ、投稿後に通知先に入ったかを取り直して確認する
- **担当者(アサイン)**: 判断や作業を頼むときは、メンションだけでなく担当者もその人に変える運用か確認する。
  担当者でないと見落とされやすい。担当者を 1 人しか設定できないツールで、1 つの課題で複数人に頼むときは、
  「作業を止めている側(ブロッカー)」を担当者にし、もう一方はメンションで届ける、などを決めて
  ユーザーに確認する
- **通知の重複**: 同じ人に短時間で複数の通知を飛ばさない。CC を外して、別コメントで「〜は○○さんに依頼済み」と書く等
- **公開範囲**: 誰が読む場所か(社内のみ/顧客も読む/公開)。内部の事情や他の人への評価を、顧客も読む場所に書かない
- **投稿の順序**: 「上のコメントで依頼しています」のように他の投稿を参照するなら、その順番で投稿する
- **場所の選択**: その論点を扱っている課題・スレッドに書く。無関係な場所に書かない

## 5. 書き方

- 先頭に要件(何をしてほしいか/何を知らせたいか)。背景は 1〜2 文
- 質問には選択肢と、それぞれを選んだときの影響を添える。相手が選ぶだけで答えられるようにする
- 相手の判断材料になる根拠(課題番号・ファイルと行番号・仕様書の該当箇所)を添える
- 社外の相手には口語体を使わない。敬語は過剰にしない
- 項目番号を書くときは、ツールの自動リンク記法と衝突しないか確認する
  (例: GitLab/GitHub で `#8` は Issue 参照になり、相手の Issue に消せない参照記録が付く。「No.8」と書く)
- URL の直前には半角スペースか改行を置く(ラベルと詰めると自動リンクにならないツールがある)
- `@` で始まるコード上の語(デコレータ、npm スコープ等)はバッククォートで囲み、意図しないメンションを防ぐ
- 長くなるなら、詳細は別の場所(PR/MR の説明、添付資料)に置き、コメントには結論と依頼だけを書く

## 6. 投稿の手順

- **下書きをユーザーに見せて承認を得てから投稿する**。承認は「その文面・その宛先・その操作」に対するもので、
  文面を直したら再度見せる
- 承認後も、投稿の直前に手順 1 の状態を軽く取り直す(下書き作成から時間が空いた場合は特に)
- 外向きの操作(投稿・担当者変更・レビュアー設定・Draft 解除など)は **1 コマンドに 1 操作**。
  まとめて実行すると、途中で止めても一部が実行済みになることがある
- 各操作のあとに状態を取り直し、意図どおりになったか(本文・通知先・担当者)を確認して報告する
- 操作が拒否・中断と返っても実行済みのことがある。続きに入る前に状態を取り直す
- 誤投稿の取り消し(削除・担当者の戻し)も通知が飛ぶ外向きの操作なので、勝手にせずユーザーに確認する

## 7. レビューを頼まれたとき

ユーザーから「この文面で大丈夫か確認して」と頼まれたら、上の 1〜4 を観点にして、
次の形で返す。

- 確認した範囲(何を取り直し、何を検索したか)
- 見つかった問題(二度聞き・事実の誤り・宛先や担当者の問題)と、その根拠
- 直した文面(直した箇所が分かるように)
- 問題が無かった観点も一言ずつ(「〜は検索したが該当なし」)。何を見ずに OK と言っているかを隠さない

「そこまで厳しく見なくてよい」と言われたら、手順 1(最新状態の取り直し)と、前回からの差分だけを確認する。
